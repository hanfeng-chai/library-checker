# A + B：公开提交的执行路径与计时边界

## 从输入到输出：这道题需要完成的全部工作

输入是两个整数 A、B，输出它们的和。例如输入 `123 456`，
输出 `579`。它没有多组测试的 T，没有大整数进位数组，也没有取模要求。
程序可以分为三步：

~~~text
文本字节 "123 456" -> 两个机器整数 123、456 -> 相加为 579 -> 文本 "579"
~~~

上游 [correct.cpp](../../../upstream/sample/aplusb/sol/correct.cpp) 用
scanf 解析两个 int，做一次加法，再用 printf 输出。类型范围是正确性的
一部分：A、B 不超过 10⁹，和不超过 2×10⁹，小于有符号 32 位上限
2147483647，因此不需要 64 位或任意精度算法才能通过本题。

为什么要在研究快解的仓库中保留这道简单题？因为它能把工具链问题与算法问题
分开观察：若这三步都无法编译、打包、读取和正确输出，先修复工具链；
若它们已正确，单次 A+B 的时间几乎无法说明复杂算法的优化价值。

## 五种读取方式究竟有什么区别

不论调用哪个库，十进制解析都要实现同一规则。逐字符解析 123 的过程是：

~~~text
x=0
读 '1': x=10×0+1=1
读 '2': x=10×1+2=12
读 '3': x=10×12+3=123
遇到空格，当前整数结束
~~~

差异在于字符怎么进入程序，以及库为定位 token 做了多少额外工作：

| 方式 | 取得数字字符的途径 | 典型额外工作 |
|---|---|---|
| scanf | 标准输入缓冲 + 格式串 | 通用格式识别、类型处理 |
| 整体读入后 split/parse | 输入字符串中的子串 | 字符串缓冲及 token 迭代 |
| 自定义缓冲扫描器 | 大块读取后移动游标 | 自己处理边界和数字 |
| mmap | 将输入文件映射为可访问内存 | 要求输入来源适合映射或提供回退 |

缓冲输出则把结果先写到用户态数组，攒够一批后再交给操作系统；
大量输出时能减少小块写入开销。但本题只输出一个短整数，
建立复杂缓冲器本身也有成本。这里不会因为模板支持 AVX2 或内存映射，
就自动得到有意义的端到端加速。

## 为什么不能从 0 ms 的排名推导“哪个解析器更强”

进程启动、运行时初始化、输入长度、计时精度都能影响这个极短程序。
五份程序记录为相同的 0 ms，只说明计时结果落在当前显示的同一精度范围，
并不是没有执行指令，也不是零延迟。即使某份在一个调用中少做几次操作，
这个计时字段也不足以把差异分辨出来。

普通可执行程序和函数提交模式的计时范围还可能不同：前者包含 main 和自行
读写，函数模式由评测框架调用用户函数。比较时先确认语言及运行模式，
不能只按毫秒字段横向排“加法算法”的速度。

需要研究解析吞吐时，应把工作量放大到
[Many A+B](../many_aplusb/analysis.md)，统一数据、编译参数与运行环境，
多次交错执行两份程序。A+B 本身则适合作为正确性与提交流程的最小例子。

## 与上游基线比较

上游只用 scanf/printf 处理两个整数，时间和额外空间均为 O(1)。
每个操作数最多 10^9，和最多 2×10^9，仍在有符号 32 位范围内；
基线的 int 加法不会溢出。公开提交分别选 i32、u32、i64，
是类型与接口选择，没有改变本题的数学运算或渐进复杂度。

逐份沿 main 的实际调用链看：

- [#376068 源码](../../selected/aplusb/376068.rs) 用 proconio
  读取两个 i64；solve 返回输出字符串，main 再打印。长文件后半部是
  打包依赖，未调用的模块不会在每次输入时执行。
- [#360939 源码](../../selected/aplusb/360939.rs) 用输入宏读取
  两个 i32，把和写入 BufWriter。MULTI 常量为 false，因此只调用
  一次 solve。
- [#341555 源码](../../selected/aplusb/341555.rs) 一次读取整个输入，
  按空白拆词解析两个 u32，再直接 println。对两个数，整体读取
  与流式读取的渐进成本没有区别。
- [#332042 源码](../../selected/aplusb/332042.rs) 用自定义 4096
  字节输入缓冲解析整数；[#318024 源码](../../selected/aplusb/318024.rs)
  按行读取并把拆出的词放进 VecDeque。后者多一些分配，但 0 ms
  计时无法测出这点成本。

个人提交中，[#389353](../../selected/aplusb/389353.cpp) 是本仓库
早期提交的普通 iostream 可执行版本，旧个人快照为 1 ms。
[#262642](../../selected/aplusb/262642.txt) 与
[#202472](../../selected/aplusb/202472.txt) 则是只含 solve 函数
的提交。#202472 原旧缓存没有排名，现已从 OJ 详情补齐 1 ms、
745472 字节、当前测试版本 AC；配置仍标为 personal_unsampled，
不能虚构其个人名次。
[#219920](../../selected/aplusb/219920.cpp) 直接使用 x86 汇编和
Linux read/write/exit 系统调用，改变的是输入输出机制，核心仍是加法。

## 仓库实现与实验价值

本地只有一份
[integer_addition.cpp](../../../problems/sample/aplusb/integer_addition.cpp)：
它使用公共 `toy/io.hpp`，从普通文件输入直接映射，调用
`read_uniform<10,u32>` 读两个数，扩展为 `u64` 后相加，最后调用
`writeln`。它比上游的 `scanf/printf` 多了一层仓库 I/O 库验证；
没有单独的 `solve.hpp` 或函数提交适配文件。
[题目配置](../../../upstream/sample/aplusb/info.toml) 列出另一份
function 参考解；跨普通可执行与函数模式的 OJ 计时不能直接比较。

本题最有价值的用途是工具链冒烟：打包、编译、读入、输出和
官方 checker 都能用极小输入核验。研究 I/O 时应改用
many_aplusb，统一编译器、输入格式和进程环境再测吞吐。
A+B 的 0/1 ms 快照只说明这些提交通过了 OJ，不能支持更细的
性能结论。本页未做新的同机 benchmark。
