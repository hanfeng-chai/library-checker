# Sparse FPS Inverse：输入只有十项，倒数仍要输出一百万项

本题求 `f(x)g(x)=1 mod x^N`。和稠密版本相比，变化在输入：
只给 `K` 个非零系数，`1≤K≤10`，而输出长度可以达到 `N=1000000`。
上游和本页前五都直接使用稀疏系数递推，没有在实际主路径上调用 NTT。
优化主要是减少每项模乘/归约、跳过尚未生效的项，以及输出成本。

## 1. `N` 是输出长度，`K` 是输入非零项数

输入第一行是 `N K`，随后 `K` 行 `(位置,系数)`。下标严格递增，
第一项的下标一定为 0，所有给定系数非零；未列出的系数都是 0。
模数 `p=998244353`，输入常数项保证可逆。

例如

```text
8 3
0 1
1 998244352
2 998244352
```

表示 `f=1−x−x² mod x⁸`。虽然输入只有 3 项，倒数为

```text
g = 1+x+2x²+3x³+5x⁴+8x⁵+13x⁶+21x⁷ mod x⁸
```

需要输出 8 项。输入稀疏不意味着答案稀疏，不能只打印答案中的
非零位置，也不能把数组长度缩成 `K`。

本题的“逆”是乘法逆，不是逐项取倒数或复合逆。常数项必须满足
`a_0b_0=1`，所以 `b_0=a_0^{-1}`。模分数表示乘模逆元；
`a_0=2` 时第一项为 `1/2`，不是实数小数。

## 2. 从乘积方程只留下非零输入项

设非常数非零项为 `(d_j,c_j)`，共 `K−1` 个。比较 `fg=1`
的第 `n>0` 项：

$$
a_0b_n+\sum_{d_j\le n}c_jb_{n-d_j}=0,
\qquad
b_n=-a_0^{-1}\sum_{d_j\le n}c_jb_{n-d_j}.
$$

所有 `d_j>0`，所以右边只引用已经求出的更低下标。零系数的项
整项消失，无需扫描从 1 到 `n` 的所有位置。

上例中只有偏移 1、2，递推成为 `b_n=b_{n−1}+b_{n−2}`，
负下标视为 0。因而 `b_1=1`、`b_2=2`、`b_3=3`，直到输出末尾。

```text
b[0] = inverse_integer(a0)
for n = 1 .. N-1:
    sum = 0
    for (d,c) in 非常数非零项:
        if d>n: break
        sum += c*b[n-d]
    b[n] = -sum*inverse_integer(a0)
```

常数逆只求一次。严格递增的输入下标使 `break` 合法；如果换成
无序稀疏容器，需要先排序，不能遇到一个大下标就认为后面都无用。

### 2.1 准确的工作量

每个偏移 `d` 实际只参与 `N−d` 项，所以内层乘积数量为
`Σ_j(N−d_j)`，至多 `N(K−1)`。加上初始化与输出，总时间
`O(NK+N)`，常说为 `O(NK)`；答案存储 `O(N)`，稀疏输入 `O(K)`。

若 `K=1`，答案只有 `a_0^{-1}` 后接零，但仍须输出 `N` 个数，
所以完整程序至少有线性输出成本。`N=1` 只处理常数。

### 2.2 在这一约束下为何不必进入 NTT

稠密 Newton 求逆需要若干轮长卷积，时间约 `O(N log N)`。
这里每个答案最多读取 9 个旧值，直接递推只有约九百万个乘积的
上界，且不用变换工作区。两种复杂度的比较应同时看 `K` 和后端
常数，不能只说“NTT 总比递推快”。

通用库可在非零项变多时切到稠密算法，但本题 `K≤10`。
下文某些源码包含庞大的 FFT/NTT 库，不表示本题调用了它们。

## 3. 上游已经使用同一稀疏递推

[题面](../../../upstream/polynomial/inv_of_formal_power_series_sparse/task.md)、
[配置](../../../upstream/polynomial/inv_of_formal_power_series_sparse/info.toml)
和[参考 correct.cpp](../../../upstream/polynomial/inv_of_formal_power_series_sparse/sol/correct.cpp)
中，`main` 直接保存输入的 `vector<pair<int,mint>>`。
它取出第一项常数，求一次逆后删去该项，按答案下标递增求值。

内层对每个非常数项检查 `i<=n`，符合条件就累加；没有利用有序性
在 `i>n` 时提前 `break`。每个乘积经过模数类型的乘法归约，
每项最后再乘常数逆。输出使用 `printf`。

因此它不是稠密二次循环，也没有重复调用通用 `inv()`。
可比较的改进是预先把常数逆并入权重、减少逐项归约、提前退出与
缓冲输出。源码 `%p` 的常量余数可能被编译器优化，不能未经汇编
检查就称每次都用了硬件除法。

### #342620：直接指定稀疏接口，不走库的自动选择

Rust `main` 用 `FPS::set` 建输入，再调用
`inverse_sparse(n−1)`。这个接口的参数是最高次数，所以传入
`N−1`，返回最多 `N` 项。它枚举非零项、跳过常数、按 `take_while`
保留 `d≤n` 的项，使用标量模乘减和常数逆。

库另有估计稀疏/稠密成本的通用 `inverse()`，但入口显式选择
`inverse_sparse`，该估计和 NTT 都不执行。结果末尾的零可被裁掉，
`main` 仍用 `get(i)` 把缺项视为零，打印完整 `N` 项，每项一行。
模乘写作 `u64` 乘积取固定模，读写使用自有缓冲。

### #307816：非零计数阈值为 50，本题始终进入稀疏分支

C++ 入口先建立长度 `N` 的稠密容器，把 `K` 项填入，调用 `inv(a)`。
`FPS::inv` 统计非零项，阈值 `SPARSE_BOARDER=50`，因此合法输入
总是走 `inv_sparse`。提取非常数项后执行与上游相同的递推，但
遇到过大下标立即退出。

构建稠密输入、统计与再次提取项都各有一次 `O(N)` 扫描，空间仍为
线性。库里的 NTT 优化分支在这里不执行。`FastRead/FastWrite`
负责实际 I/O，不能按头文件中的普通流或 NTT 模块判断成本。

### #400461 / #405984：把每个答案的多次归约合并为一次

正规化换行后两份源码逐字相同。`main` 创建稠密数组，然后明确
调用 `inv_sparse`；提取非零项后，先把每项权重变成
`w_j=−c_j/a_0`，从而递推是 `b_n=Σw_jb_{n-d_j}`，省去每项
末尾再乘一次常数逆。

`sparse_dot` 在模数小于 `2^30`、项数不超过 16 时，用
`uint64_t` 累加普通整数乘积，整段结束后只做一次模约减。
本题非常数项至多 9 个，满足这条路径。正确性不仅靠“项少”，还靠
所有因子都已规范到 `[0,p)`，并且

$$
16(p-1)^2<2^{64}.
$$

换成更大的项数或模数必须恢复分段归约。这个热循环是短标量点积，
不能因为打包文件有 SIMD FFT 就称本题执行了向量 FFT。
两份都使用 `blazingio`，可见算法差异不能解释 28/29 ms 的波动。

### #375636：直接保存稀疏表，递推时包含一个零贡献的常数项

Rust 入口构造 `SparsePolynomial`，直接调用 `f.inv(n)`，没有
创建长度 `N` 的输入表再扫描。答案数组预置为零，按下标递增求值。

该 `inv` 的内层包含 `(0,a_0)`，但读到的是当前尚未写入的
`g[i]=0`，所以这一项贡献为零；结束后才给 `g[i]` 赋值。
数学正确，但每轮比显式排除常数多检查/计算一项，复用到非零旧缓冲
时也不能忽略初始化条件。

输出使用缓冲数字写入。输入是直接的 `K` 项对象、没有 NTT 调用，
不能把文件里其他稠密多项式接口的复杂度算入本题主路径。

## 5. 如何验证优化没有改掉递推

| 可改的部分 | 减少什么 | 需要的条件 |
|---|---|---|
| 提前 `break` | 偏移尚未生效时的多余检查 | 非零下标有序 |
| 权重预乘 `−a_0^{-1}` | 每个输出末尾的常数乘法 | 常数非零，权重按模规范化 |
| 整段 `uint64_t` 求和 | 每项单独模约减 | 证明最大项数乘最大乘积不会溢出 |
| 直接使用稀疏表 | 稠密输入清零和扫描 | 仍需 `O(N)` 的答案数组 |
| 缓冲输出 | 百万个整数的格式化/接口开销 | 仍必须输出所有零项 |

输入只有至多十行，读取并非大数据量；输出最多一百万个数，数字
转换与缓冲对整程序时间影响不能省略。各 `b_n` 依赖更低项，不能
未经依赖分析就把连续答案放到不同 SIMD 槽位同时求。

已核对五份源码哈希、调用路径及重复文本关系。本地以 128 组长度 `1..32`、至多 10 项的随机稀疏输入比较直接
递推与预缩放权重，且全部通过 `f*g mod x^N=[1,0,…,0]` 检查；
另计算核对了 64 位累加的整数上界。本页不新增编译、OJ/API 请求或性能测试。

边界应覆盖 `N=1`、`K=1`、首项不为 1、最小偏移为 1、最大偏移
为 `N−1`，以及所有非常数项到末尾才生效的输入。
若要讨论切换 NTT 的阈值，应另行扩大 `K` 并统一 I/O 与模数后端，
当前快照不足以证明某个阈值或算法族在全站最优。
