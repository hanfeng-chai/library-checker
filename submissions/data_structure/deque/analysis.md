# Deque 公开快解拆解

## 先用七次操作看懂题目

双端队列是一条能从两端增删的序列。本题还允许直接读出第 i 个元素，
下标从 0 开始。队列最初为空，操作码 0、1 表示头部/尾部插入，
2、3 表示头部/尾部删除，4 表示按下标访问。

| 输入操作 | 操作后的序列 | 输出 |
|---|---|---|
| 1 7：尾插 7 | [7] | |
| 0 3：头插 3 | [3,7] | |
| 1 11：尾插 11 | [3,7,11] | |
| 4 1：读下标 1 | [3,7,11] | 7 |
| 2：删头 | [7,11] | |
| 3：删尾 | [7] | |
| 4 0：读下标 0 | [7] | 7 |

这里既要“能从两边改”，也要“能按位置读”。如果直接用普通连续数组，
每次头插都把现有元素往右搬一格，那么连续 Q 次头插要搬
0+1+…+(Q−1) 个元素，是 O(Q²)。如果改成双向链表，两端修改虽然方便，
找第 i 项又需要顺着指针走 O(i) 步。这两个直观表示各自有明显瓶颈。

## 一般做法：上游如何同时支持两端修改与随机访问

[上游 correct.cpp](../../../upstream/data_structure/deque/sol/correct.cpp)
采用标准库 std::deque。可以把典型实现理解成“若干小数组块 + 一个块指针目录”。
目录记录每块的位置，队首记录从哪块、哪一格开始；查询先算目标落在哪块，
再取该块内的位置，因此不用像链表那样逐个经过前驱元素。

例如每块能放 4 个数，逻辑队首位于块内偏移 2，第 5 个元素的位置由
2+5=7 决定：向后跨 1 块，块内偏移 3。末端需要新空间时增添数据块，
已存在的数据通常不必整体搬家。实际块长和分配策略由标准库实现决定，
题目源码并没有自己管理这些细节。

所以 correct.cpp 的全部业务逻辑可以逐行对应：

~~~text
0 x -> que.push_front(x)
1 x -> que.push_back(x)
2   -> que.pop_front()
3   -> que.pop_back()
4 i -> printf(que[i])
~~~

标准 deque 为这些操作提供常数复杂度接口；总工作量线性于操作数。
相对于这个已经合适的基线，榜首的数组实现没有再把 O(Q²) 变成 O(Q)；
主要省掉的是分段寻址、块边界判断、动态存储管理和 I/O 的常数开销。

## 利用“操作总数已知”，把序列放在数组正中间

给定最多 Q 次操作，可以预留约 2Q 个槽位，把空队列放在正中间。
令有效范围为半开区间 [L,R)，则大小是 R−L，操作如下：

~~~text
push_front(x): data[--L] = x
push_back(x):  data[R++] = x
pop_front():  ++L
pop_back():   --R
get(i):       data[L+i]
~~~

半开区间的含义是“包含 L、不包含 R”。当 L=R 时没有元素，
因此空队列也无需特殊占位。上面的七次操作若从 L=R=8 开始：

| 操作之后 | L | R | 当前有效槽位 |
|---|---:|---:|---|
| 空队列 | 8 | 8 | 无 |
| 尾插 7 | 8 | 9 | data[8]=7 |
| 头插 3 | 7 | 9 | data[7..8]=[3,7] |
| 尾插 11 | 7 | 10 | data[7..9]=[3,7,11] |
| 读下标 1 | 7 | 10 | 读 data[8]=7 |
| 删头 | 8 | 10 | [7,11] |
| 删尾 | 8 | 9 | [7] |

每一步都只改一个游标，插入/查询再访问一个槽位。正确性不变量是：
data[L],…,data[R−1] 始终按顺序等于题目中的序列。每种操作都恰好
在这个区间的对应端扩张或收缩一格，因此可以直接归纳证明。

为什么不会撞到数组边界？关键条件是**总共最多 Q 次操作**：
一个游标每步最多移动一格，从中央开始最多偏移 Q 格。
仅知道“同时存在的元素不超过 Q”还不够；若允许无限操作，反复删头再尾插，
即使队列长度始终为 1，居中数组也会一直向右漂移。本题的总操作数上界
排除了这个问题，所以无需搬回中间，也无需回绕。

## 另一条路线：循环数组怎样工作

循环队列只分配约 Q 个槽位，保存 head 和 size，把逻辑下标 i 映射到
(head+i) mod capacity。例如容量 8、head=7、size=2 时，
逻辑 [3,7] 可以存于 data[7]=3、data[0]=7。尾插 11 写到 data[1]，
读下标 1 访问 data[0]，删头只把 head 改成 0 并减小 size。

它比居中数组节约了预留的空槽，但每次操作要处理跨末端回绕。
容量若为 2 的幂，可用位与代替一般取模；若不是，也可以用条件减法，
所以“循环数组必定执行昂贵整数除法”并不成立。Rust 的 VecDeque
就是可用的环形缓冲容器；本题 #369796 提前 with_capacity(q)，
让执行中不必因队列增长而再扩容。

| 表示 | 怎样访问第 i 项 | 空间取舍 | 热路径额外工作 |
|---|---|---|---|
| 标准分段 deque | 块目录 + 块内偏移 | 随元素与数据块增长 | 分段寻址和边界管理 |
| 定长循环数组 | (head+i) mod C | 约 Q 个槽 | 回绕计算 |
| 定长居中数组 | L+i | 约 2Q 个槽 | 无回绕，无分段 |

这三种都能达到本题需要的线性总时间。后面的排名比较应放在这个共同背景下看。

## 第一名额外利用了什么：值只被保存、原样读出

假设一个插入值 17 的十进制文本位于输入文件字节偏移 100，长度为 2。
如果后续从不对它加减、比较大小，只要求输出这个值，可以保存“偏移 100、
长度 2”而不解析成整数 17。查询时直接复制那两个字符，再输出分隔符。

#400806 把位置和长度压到一个槽里：

~~~text
encoded = (offset << 4) XOR length
offset  = encoded >> 4
length  = encoded AND 15
~~~

offset 左移后的低四位为 0，长度小于 16，所以这里 XOR 与按位 OR 效果相同。
上例编码为 1602，解码后仍是 100 和 2。数据结构依然是居中数组，
但省去了“十进制字符 -> 整数”和“整数 -> 十进制字符”两次值的转换。
队列下标仍须解析，操作码仍须识别，输入文件也要一直保持可访问。

这项技巧依赖具体任务：如果新增“给所有元素加一”，原文本就不再是答案；
如果输入允许非标准数字文本，原样输出是否符合要求也要重新检查。
本题官方输入是规范数字，并且每个值后有换行，源码据此连换行一起复制。
理解这个条件后，再看 mmap、字节偏移、SWAR 找 token 边界等细节就容易得多。

## 如何读后面的五份源码

先找保存元素的那个容器和左右边界，再看操作码如何更新它，最后研究 I/O。
例如 #327841 插入时同时写 head−1 和 tail，真正纳入有效区间的只有一侧；
另一写入仍在区间外，是用多一次写入换较少分支的实现选择。
这类改动要对照分支预测和访存测量，无法由“代码看起来更底层”判断输赢。

## 普通基线与居中数组

[上游 `correct.cpp`](../../../upstream/data_structure/deque/sol/correct.cpp) 直接用 `std::deque<int>`，每次操作按题意调用容器接口，以 `scanf`/`printf` 读写。标准双端队列提供两端插删与下标访问的常数复杂度，但典型实现分段存储，索引需跨块定位；标准输入输出也要做通用格式解析。

若操作总数为 `Q`，可在约 `2Q` 个槽位的连续数组中把空队列表示为中点的半开区间 `[L,R)`：队首插入写 `a[--L]`，队尾插入写 `a[R++]`，两端删除只移动相应游标，访问 `a[L+i]`。最多 `Q` 次操作意味着 `L` 向左及 `R` 向右各自最多走 `Q` 步，不会越过两端。这个表示的每次操作都是最坏 `O(1)`，空间 `O(Q)`；省去了循环队列的回绕与取模，也不用标准容器的分段索引。代价是提前占用两侧最大容量，只适用于预先知道操作上界的场合。

上述不变量也给出正确性：空区间对应空序列；插入只在相应端扩一格并写新元素；删除只缩一格；因此连续区间始终依次等于抽象队列，第 `i` 项自然是 `a[L+i]`。

## #362377：直接存整数的数组基准

[#362377 源码](../../selected/deque/362377.cpp) 用静态 `uint32_t pool[2N]`，令 `l=pool+N`、`r=pool+N-1`。它把有效区间写成闭区间 `[l,r]`：队首插入 `*--l=x`，队尾插入 `*++r=x`，删除移动对应指针，查询直接读 `l[i]`。空队列时 `l=r+1`，因此与上一节半开区间只是记号不同。主算法没有复杂预处理，也没有动态分配；快输入使用 mmap 和手写整数解析，输出使用缓冲区。

和上游相比，可明确归因的结构改动是连续内存、无分段寻址；手写 I/O 同样参与最终时间。OJ 7 ms 不能拆成各项优化的独立收益。

## #400806：把原始输入当作值的存储

[#400806 源码](../../selected/deque/400806.cpp) 仍用居中数组，但插入时不把 `x` 转成数值。输入文件先被 mmap；每个元素槽位存 `offset<<4 ^ length`，其中 `offset` 是十进制 token 在输入中的字节偏移，`length` 是 1–10 位数长。查询时解码位置和长度，直接把原 token 连同换行符复制到输出缓冲区。这避免了对插入值做十进制转整数、再对查询结果转回十进制。`Q` 与查询下标仍须解析，源码的 `parse6` 用 64 位字读取并批量运算十进制位；`digit_count10` 也通过 64 位字判别数字长度。值本身不参与计算，是这项优化成立的根本原因。

表示需要 `length<16` 且字节偏移能放进剩余位；本题值至多 10 位，输入量也在该编码的范围内。源码假定标准输入是可 mmap 的普通文件，依赖值 token 后紧接换行，并将原有文本原样输出；若放到支持管道输入、任意空白或要求数值规范化的通用双端队列任务，就不能直接沿用。它的 14.99 MB OJ 内存也高于其余前五，包含静态数组与一次性输出缓冲区；不能把这一排名解释成新的双端队列算法。

## #327841：减少插入分支的 Rust 居中数组

[#327841 源码](../../selected/deque/327841.rs) 也在 `2Q` 静态槽位的中间令 `head=tail=Q`。遇到插入，它把 `x` 同时写到 `a[head-1]` 和 `a[tail]`，再依据 `op=0/1` 只移动一侧游标。真正有效的仍只有更新后 `[head,tail)` 中新增的一格；另一写入落在当前有效区间外，属于用额外写入替换分支的工程权衡。删除 `op=2/3` 用算术式移动对应游标，查询取 `a[head+i]`。输出借助 `itoap` 写到缓冲区。

这个写法没有改变渐近复杂度，反而每次插入多一次内存写入。源码对输入缓冲区做单次 `read`，随后用 unchecked 下标解析，适合当前 OJ 输入方式；把它移到可能短读的流时需要补全读取逻辑。不能只看 `unsafe` 或无分支就认定比 #362377 快，两者 OJ 时间反而为 10 ms 与 7 ms。

## #369796、#364924：标准容器配快 I/O

[#369796 源码](../../selected/deque/369796.rs) 使用 `VecDeque<u32>::with_capacity(q)`，以环形缓冲实现两端操作和索引；预留 `q` 容量使本题执行中不需要因队列增长而扩容。它的 I/O 层对普通文件 mmap，对其他输入读到缓冲区。算法与上游同属标准容器路线，差异主要是 Rust 容器实现和 I/O 路径。

[#364924 源码](../../selected/deque/364924.cpp) 的 `Yorisou()` 仍是 `std::deque<int>` 的 `emplace_front/back`、`pop_front/back`、`q[x]`，与上游的核心数据结构相同。其大段模板包含自定义快速读写。因此这份结果说明通用双端队列仍可进入前五，而不能把 11 ms 相对上游的潜在差距说成新算法贡献。

## 与本仓库实现的关系及下一步

保留的个人 [#393897 源码](../../selected/deque/393897.cpp) 是本仓库 [`centered_array.cpp`](../../../problems/data_structure/deque/centered_array.cpp) 的提交版，同属存整数的居中数组路线，不应因排名第六以外就删除。其 `rank.scope=personal:chaihf`，与前五不同用户名次不直接可比。[本地题解](../../../problems/data_structure/deque/tutorial.md) 记录：同机、同编译参数下，36 个官方用例全通过；在 `max_random_00`，本地居中数组相对公开 #362377 的 `perf` cycles 为 `0.965x`，指令数为 `0.848x`。这是单一用例、固定环境的证据，不能推出 OJ 总时间必定更短。
