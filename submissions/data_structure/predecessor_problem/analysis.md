# Predecessor Problem：从扫描空位到位图、秩选择与 vEB

## 题目与完整手算例：查询包含端点本身

维护 `[0,N)` 中的一个整数集合 `S`，初始状态由长 `N` 的 01 字符串给出：
第 `i` 个字符为 `1` 当且仅当 `i∈S`。约束 `N≤10000000、Q≤1000000`，
操作码的含义为：

| 操作 | 要做什么 | 是否输出 |
|---|---|---|
| `0 k` | 插入 `k`；已经存在就保持不变 | 否 |
| `1 k` | 删除 `k`；本来不存在就保持不变 | 否 |
| `2 k` | 判断 `k` 是否在集合中 | 输出 0 或 1 |
| `3 k` | 找最小的 `x∈S`，使 `x≥k`，称后继 | 找不到输出 -1 |
| `4 k` | 找最大的 `x∈S`，使 `x≤k`，称前驱 | 找不到输出 -1 |

后继和前驱都**包含 `k` 本身**。一些库的同名函数采用严格大于/小于，
因此读 `main` 时必须核对传入的是 `k`、`k-1` 还是 `k+1`。
下面是一份完整输入，初始集合为 `{1,4,6,10}`：

```text
12 13
010010100010
2 4
3 5
4 5
0 5
3 5
1 4
2 4
1 10
3 7
4 11
0 5
1 0
4 0
```

| 操作 | 操作后的集合 | 输出及原因 |
|---|---|---|
| `2 4` | `{1,4,6,10}` | `1`，4 存在 |
| `3 5` | 同上 | `6`，最小的不小于 5 的键 |
| `4 5` | 同上 | `4`，最大的不大于 5 的键 |
| `0 5` | `{1,4,5,6,10}` | 无 |
| `3 5` | 同上 | `5`，端点也算 |
| `1 4` | `{1,5,6,10}` | 无 |
| `2 4` | 同上 | `0`，4 已删除 |
| `1 10` | `{1,5,6}` | 无 |
| `3 7` | 同上 | `-1`，右边没有元素 |
| `4 11` | 同上 | `6` |
| `0 5` | 同上 | 无，重复插入没有增加第二个 5 |
| `1 0` | 同上 | 无，删除不存在的键也不改变集合 |
| `4 0` | 同上 | `-1`，左边没有元素 |

所以输出依次为 `1,6,4,5,0,-1,6,-1`，各占一行。

## 从最直观的扫描法出发

存一个布尔数组 `present[0..N)`，插入、删除、成员查询只访问一个位置，
均为 `O(1)`。后继则直接向右找第一个 1：

```text
successor(k):
    for x = k .. N-1:
        if present[x]: return x
    return -1
```

前驱对称地从 `k` 向左找。第一次遇到的存在元素就是距离最近的合法答案，
所以正确；问题在空洞。空集合或稀疏集合中，一问可能查看 `N` 个位置，
最坏 `NQ=10^13` 次检查。即使把 64 个布尔值压进一个整数，若仍逐字
寻找下一个非零字，最坏也要扫 `N/64` 个字，尚未解决跨长空段的问题。

平衡搜索树是另一条直观路线：只保存存在的 `K=|S|` 个键，维护它们的大小
顺序，查找边界和增删通常为 `O(log K)`。它适合稀疏、巨大或未知值域，
但每个键需要节点和链接；本题值域已知且最多一千万，更适合按**位置**建
紧凑索引。上游有 [`set.cpp`](../../../upstream/data_structure/predecessor_problem/sol/set.cpp)
供对照，不过 `correct.cpp` 实际使用下面的 64 叉树。

## 一字内怎样同时检查 64 个位置

一个 64 位无符号整数的第 `b` 位表示一个键是否存在，最低位对应最小键。
键 `k` 的字下标是 `j=k/64`，字内位置是 `b=k%64`。
插入做 `word[j] |= 1ULL<<b`，删除做 `word[j] &= ~(1ULL<<b)`；
位 OR 重复置 1、位 AND 重复清 0 都没有副作用，正好符合集合语义。

设某字只有第 `1,4,6` 位是 1，写低八位为 `01010010₂`。要找本字内
不小于位置 3 的键，先清掉低三位，得到 `01010000₂`，最低的 1 在位置 4。
`ctz(x)` 是从最低端数连续 0 的数量，对这个掩码得到 4；
`clz(x)` 是从最高端数连续 0 的数量，故 `63-clz(x)` 是 64 位字最高 1
的位置，用于前驱。两种操作可由固定数量的机器指令完成。

实作可用 `word>>b` 查后继，再把 `ctz` 得到的相对偏移加回 `b`；
前驱可用 `word<<(63-b)`，再以 `b-clz(结果)` 得到位置。
必须先判掩码非零：传统 `__builtin_ctzll(0)/clzll(0)` 没有有效的位号。
也不能写会在 `b=63` 时移位 64 的表达式；“保留到 b 位”的数学公式
必须用边界分支或始终小于 64 的移位实现。这是固定字宽位技巧的正确性条件。

## 沿上游 `correct.cpp` 走：64 叉树如何跳过整片空区间

### 节点摘要和键的高低位

把键写成 64 进制，相当于每次取六个二进制位。本题最多需 24 位，
`w_ary_tree<4>` 有四层：从最高六位选根的孩子，再取下一组六位，最后
最低六位在叶字中定位。一个高度为 `LOG` 的节点使用
`shift=(LOG-1)*6`，`pos=key>>shift` 是孩子号，低 `shift` 位是传给
孩子的局部键。叶节点 `LOG=1` 就是前面的一字位图。

上游节点除 64 个孩子外，还保存以下摘要：

| 成员 | 精确含义 | 用途 |
|---|---|---|
| `map` | 第 `b` 位为 1 当且仅当第 `b` 个孩子非空 | 一次位扫描跳到下个非空孩子 |
| `mn` | 本节点内最小的局部键，空时为 `inf` | 直接返回子树最小值 |
| `mx` | 本节点内最大的局部键，空时为 -1 | 判断当前孩子是否还可能有答案 |
| `chd[64]` | 每个孩子维护下一段低位 | 下探到更小的值域 |

这里 `chd` 是嵌套的 `std::array`，整棵树是一个静态对象，**不是逐节点
动态分配的指针树**。后面的快解改变的是按层平铺的布局及摘要内容，
不能把省掉 malloc 说成相对上游的收益。上游固定覆盖 `2^24` 个键，
即使实际 `N` 更小，整个对象也存在。

### 上游查询与更新的实际路线

以集合 `{1,6,130,132,450}` 查询后继 `≥133`。高层的键都落在第 0 个
大区间，递归来到每个孩子覆盖 64 个键的节点。此时 `pos=2`、低位为 5；
孩子 2 内只有局部键 2 和 4，因此其 `mx=4<5`，不必进入孩子搜索。
父节点的 `map` 只有孩子 `0,2,7` 非空，屏蔽不大于 2 的位后，最低 1
是孩子 7。直接读取该孩子的最小值 2，拼回 `7*64+2=450`。

`find_next` 从顶层往下：若 `key≤mn`，整节点最小值就是答案；否则先用
`map` 和当前孩子的 `mx` 判断它能否容纳答案，能才递归。不能则用 `ctz`
选择更靠后的非空孩子，并利用已存 `mn` 返回其最小键。
`find_prev` 对称，但它的接口是**严格小于 key**；`main` 调用
`find_prev(k+1)` 才实现题目的 `≤k`。叶子里的截断掩码也遵守这个严格语义。

插入一路更新 `mn/mx`、置孩子占用位，直到叶字置位。删除先递归删叶位；
孩子变空才清 `map`，若删掉了本节点 `mn` 或 `mx`，还要从剩余非空孩子
重新取极值。以删除 450 为例，孩子 7 清空、对应占用位清零，最大值改为
孩子 2 的最大局部键 4，拼回 132。每层只涉及一条更新路径和常数次位操作。

`main` 先逐字符读初始串，对每个 1 调用 `insert`；随后用 `scanf/printf`
处理操作。令层数 `H=ceil(log₆₄U)`、`U` 为覆盖宇宙，更新和边界查询
`O(H)`，本题 `H=4`。初始串有 `K` 个 1 时，这条初始化路径做
`O(N+KH)` 的读入和插入；注释写 `O(N+Q log₆₄N)` 是把本题固定的四层
初始化计为线性。快解没有把一个普通搜索树凭空变成常数查询，主要是继续
减少这四层里做的工作，并用一次批量构建替代 `K` 次完整插入。

## 从上游变到快解：每层只保留非空位图

### 四层数组的不变量

不存每个内部节点的 `mn/mx` 也可以找极值：找到一个非空大块后，逐层选
最低的 1 就得到最小键，逐层选最高的 1 就得到最大键。于是用每层一段
连续的 64 位数组，保存如下信息：

| 层 | 每一个 1 代表什么 | 该层一个字覆盖多少原键 |
|---|---|---:|
| `L0` / `leaf` | 一个存在的原键 | 64 |
| `L1` / `lv12` | 一个非空的叶字 | 4096 |
| `L2` / `lv18` | 一个非空的 `L1` 字 | 262144 |
| `L3` / `root` | 一个非空的 `L2` 字 | 16777216 |

形式化地，对 `h>0`，`Lh[j]` 第 `b` 位为 1，当且仅当
`L(h-1)[64j+b] != 0`；所有超出 `N` 的填充位保持 0。
这意味着“父层没有标记的整块一定无解”，也是跳过长空洞的根据。

### 手走一次上升、下降与更新

为了让位图可画在一行，下面**只在示意中**把字宽从 64 改成 8，键域取
`[0,256)`、集合取 `{1,6,18,20,130}`。真实程序仍是 64 位和六位一组。
非零叶字为 `L0[0]=01000010`、`L0[2]=00010100`、`L0[16]=00000100`。
再向上归约：

```text
L2[0] = 00000101              // L1 的字 0、2 非空
L1[0] = 00000101              // L0 的字 0、2 非空
L1[2] = 00000001              // L0 的字 16 非空
其他字均为 0
```

找后继 `≥21`：

1. `21=2*8+5`，检查叶字 2 从第 5 位开始的部分，为零。
2. 上升到 `L1[0]`，寻找严格大于孩子号 2 的置位，也为零。
3. 再上升到 `L2[0]`，寻找严格大于孩子号 0 的置位，找到 2，确定下一片
   非空区域是 `L1[2]`。
4. 下降，`L1[2]` 最低置位为 0，得到叶字号 `2*8+0=16`；该叶字最低
   置位为 2，得到原键 `16*8+2=130`。

找前驱 `≤129` 完全对称：当前叶字 16 的第 0、1 位为空；父层也没有更早
孩子，于是在根选靠前的字 0，再依次选最高置位 2 和 4，得到 `2*8+4=20`。
整个过程从未遍历键 21 到 129 中间的空位。

删除 18 只清掉 `L0[2]` 的第 2 位，字中还有 20，所以上层完全不变。
再删除 20，叶字 2 才变空，须清 `L1[0]` 第 2 位；`L1[0]` 还有第 0 位，
传播在这里停止。删除 130 则会令叶字 16 和 `L1[2]` 都变空，必须再清
根的第 2 位。插入按空变非空的相反过程传播。这解释了“仅状态变化时更新
上层”为何正确，也解释了它到底少写了哪些数组位置。

查找先检查当前叶字，失败才上升找更早/更晚的非空兄弟，再逐层下降。
上升时必须**排除当前孩子**，因为它在所需方向已查失败；否则可能反复选回
同一个块。下降时所选字由占用不变量保证非零，可以安全做位扫描。
找不到任何兄弟就返回 -1，空集合也自然走这条路径。

一次查找最多 `O(H)` 次上升和下降；成员查询直接查叶位，为 `O(1)`。
变长分配的位图总存储约 `N/8*(1+1/64+1/64²+…)` 字节，
`N=10000000` 时约 **1.27 MB，即 1.21 MiB**，另计取整、容器和 I/O 缓冲。
固定四层在本题是小常数，推广到更大宇宙时仍是 `O(log₆₄U)`，不能把它
写成与宇宙大小无关的一般 `O(1)`。

### 初始串怎样一次建好

先把连续 64 个字符打包成一个叶字，再扫描叶字是否非零生成上一层，
重复直到根。这不需要对每个 1 都重走四层。以 #278227 的 AVX2 路径为例，
一个寄存器的 32 个字节槽各装一个输入字符；与字符 `'1'` 逐槽比较后，
每槽变成全 1 或全 0；`movemask` 取各槽最高位，合成 32 位掩码。
两次合在一起就是一个 64 位叶字，尾部不足一整组时按实际长度处理。
上层再把“下层字是否为零”转换成位即可。

读 `N` 个字符仍是 `O(N)`，不能声称读入降成 `O(N/64)`；减少的是
逐字符判断和重复访问祖先摘要的指令数。#269275 还并行比较四个相邻
64 位叶字是否为零，把上层占用位的构建也批量化。稠密初始串省下的重复
插入最多，空初始串本来就没有这部分插入成本，收益来源会不同。

## 当前前五的实际差异

### #403023：小集合缓存与可变方向查找

[`403023.cpp`](../../selected/predecessor_problem/403023.cpp) 的 `main` 实例化
`adaptive_bounded_integer_set`，不是源码中的其他备用容器。其底层
`bitmap_hierarchy` 仍用连续的叶字和占用父字；与上游每结点存 `mn/mx`
且沿递归子树搜索不同，实际修改路径
`set → bounded_integer_set::set → bitmap_hierarchy::assign`
只在叶字空/非空状态变化时向上传播。
正常大集合先检查当前叶字，失败才调用按模板展开的 `ascend/descend`；
前驱和后继共用方向参数及掩码选择。

这份提交的额外技巧是 `size() ≤ 16` 时改查 16 元素的排序缓存 `small_`。
每次更新标记缓存脏；下一次范围查询才经位图迭代重新生成，随后用 AVX2
比较 16 个 `u32`、收集掩码和 `popcount` 算出前驱/后继位置。连续查询且
没有更新时可重复使用。重建至多枚举 16 个键，每键调用底层查找；该路径
对稀疏测试尤其有意义。`size()>16` 时使用常规四层位图。

缓存查找本质上是在求一个很短的有序数组中的秩。例如缓存为 `[1,5,6]`：
后继 `≥5` 先数严格小于 5 的元素，共 1 个，于是取第 2 个元素 5；
前驱 `≤5` 先数严格小于 6 的元素，共 2 个，于是取第 2 个元素 5。
源码把真实键放在 `small_[1..K]`，两端与未用槽填 `npos=N`，
后继返回 `small_[rank+1]`，前驱返回 `small_[rank]`；没有合法答案时
自然落在哨兵槽。空集合在更前面直接返回。

AVX2 两组寄存器各装八个缓存键，每槽和同一阈值比较，得到 16 个真假结果；
收集成 16 位掩码后，`popcount` 数 1 的个数就是秩。缓存是有序的，
所以计数还能直接当成答案位置。源码对每个 32 位值翻转最高位，再做有符号
比较，以保持原来的无符号大小顺序；这也让填充值按预期留在键的右侧。
这里向量化的是 16 个候选与一个阈值的比较，没有并行执行 16 条集合操作。

实际 `main` 的修改入口是 `set(key,present)`，每次调用都会令 `dirty_=true`，
即使是重复插入/删除。下一次范围查询才重建。稳定小集合上的连续查询可
摊薄重建代价；若每次查询前都修改，最坏每次都要重新枚举至多 16 个键，

归约；整数 I/O 使用映射文件读取和自有写缓冲。16 ms 是这些因素的合计，
不能把比 20 ms 少的 4 ms 全归因于小集合缓存。

### #76516：真正的 van Emde Boas 递归

#### 高低分解为什么会把递归深度再缩短

层级位图每层剥掉六个二进制位，剩余位数是 `B-6`。van Emde Boas，
简称 vEB，改成把 `B` 位键大约对半切开：

```text
R = ceil(B/2)                // 低位数
high(x) = x >> R            // 簇号
low(x) = x & (2^R-1)        // 簇内键
x = high(x)*2^R + low(x)
```

每个高位簇中的低位键用一棵较小的 vEB 树 `ch[high]` 存；哪些簇非空，
再由另一棵 vEB 树 `act` 保存簇号。`B=24` 时先变为 12 位，再变为 6 位，
而该源码对 `B≤6` 直接用一个 64 位字。因此关键递归层数是位数减半的次数
`O(log B)=O(log log U)`，其中 `U=2^B`。

**这份源码把两个极值都单独存放。** 节点的 `mi/ma` 保存本集合最小、最大键，
`ch` 只保存两者之间的其余键；`act` 也只记录这些内部键所在的非空簇。
集合只有一两个键时，可能所有 `ch` 都为空。不能照搬“子簇含所有元素”
或“只把最小值放在外面”的另一个 vEB 版本来解释它。

#### 一个查询在簇里如何走

取 `B=8、U=256、R=4` 的实际同类小实例，集合为
`{3,6,19,22,54,201}`。节点单存 `mi=3、ma=201`，其余键为：

| 高位簇号 | 原键 | 存入 `ch` 的低四位 |
|---:|---|---|
| 0 | 6 | `{6}` |
| 1 | 19,22 | `{3,6}` |
| 3 | 54 | `{6}` |

`act={0,1,3}`，不含仅存于全局最大值的簇号 12。查询按下面三条路径走：

| 后继查询 | 当前簇 | 当前簇失败后的动作 | 答案 |
|---|---|---|---:|
| `≥20` | `high=1,low=4`，簇 1 中找到 6 | 无需查摘要 | `1*16+6=22` |
| `≥23` | `high=1,low=7`，簇 1 最大才是 6 | `act` 找簇号 `≥2` 得到 3，取其最小低位 6 | 54 |
| `≥55` | `high=3,low=7`，本簇失败 | `act` 找不到更后簇，返回单存的 `ma` | 201 |

前驱 `≤18` 的高低位为 `1,2`，簇 1 无合适低位，于是在 `act` 找更前簇 0，
取该簇最大低位 6，得到 6。若所有更前簇都为空，返回单存的 `mi`。
查询在极值范围外时更快：`findNext(i)` 若 `i≤mi` 直接返回 `mi`，
若 `i>ma` 返回本节点宇宙大小；前驱对称返回 -1。

为什么“试当前簇，又查 act”没有产生两棵都深入的递归？当前簇只有确实
可能含答案时才深入；如果失败，是其极值范围已排除答案，会立即返回。
查到下一簇后，取它的最小/最大值又是常数工作。因此每个尺度至多一条
实质搜索路径，递推为 `T(B)≤T(ceil(B/2))+O(1)`。

#### 更新为什么必须同时维护极值和活跃簇

分别从原集合考察三个独立更新。插入 2：新最小值放入 `mi=2`，旧最小值 3 变成内部键，
插入簇 0。删除 54：簇 3 的最后一个键消失，还须从 `act` 删除簇号 3，
否则以后的查询会沿摘要走进空簇。删除原最小值 3 时则先找新的最小值 6，
把它提升到 `mi`，再从簇 0 删除这个 6；提升后的极值不能继续在子簇中
重复保存。`ma` 的维护是对称的。

新建非空簇需要更新 `act`，此时向原空子簇插入第一个键是常数操作；
删除最后一个键时清空子簇也是常数操作，剩下的递归在摘要中。
这与前述查询一起给出增删和边界查找 `O(log log U)` 的操作界。
但初始化不是一次普通插入：`main` 先读成完整 `Bitset<2^24>`，再用
`init` 遍历预分配簇，切出各自对应的位图片段并建立摘要。
这份结构的内存随整个 `U` 增长，含约 `U/64` 个叶字及内部簇信息，
按固定机器字宽可记为 `O(U)` 空间；初始化也有遍历宇宙结构的成本，
不能标成一次 `O(log log U)` 操作。稀疏集合不会自动使静态 `ch[]` 变小。

[`76516.cpp`](../../selected/predecessor_problem/76516.cpp) 的 `main`
实例化 `VEBTree<24>`，并调用 `veb.init/insert/erase/findNext/findPrev`；
这不是源码里另有的普通位图辅助类。一个结点把 `B` 位整数拆成高位簇号
和低位簇内值，保存 `mi/ma`、各簇 `ch[]` 和记录非空簇的 `act`。查找先
尝试当前簇，失败后在 `act` 中找下一个/上一个非空簇，再取其最小/最大；
插删还要维护极值和簇的空/非空状态。`B≤6` 的递归叶子才退化为一个
64 位掩码。递归深度约 `O(log B)=O(log log U)`，与固定四层层级位图的结构
确有区别。初始 01 串先打包为 `Bitset<2²⁴>`，然后 `veb.init(ini)` 构树；
内存会为递归簇和初始位图付费，工程常数及构建路径也不同。候选池中
#211007 与它源码完全相同，时间 49 ms；#76699 则是同族另一个版本，
50 ms。48 ms 只说明这份具体实现的快照成绩，不代表 vEB 理论上比位图慢。

### #234854：局部位图与 Fenwick 选择

#### 从“有没有元素”换成“有几个元素”

层级位图的摘要只存一位：下方是否非空。若改存元素数，就能回答另一类
问题：“前面共有多少元素”和“排序后的第几个元素在哪里”。称前者为
**秩**、后者为**选择**。后继 `≥k` 是第 `count(x<k)+1` 个元素；
前驱 `≤k` 是第 `count(x≤k)` 个元素。若所需排名超出总元素数，答案不存在。

Fenwick 树，也称树状数组，用少量区间计数支持前缀和。教学使用从 1
开始的下标，`tree[j]` 保存区间 `[j-lowbit(j)+1,j]` 的和。
求前缀和时不断 `j-=lowbit(j)`，得到若干不重叠片段；某个计数改变时，
不断 `j+=lowbit(j)`，更新所有包含它的摘要。每一步改变一个二进制位，
所以都是 `O(log M)`，`M` 为被计数的对象个数。

本提交被计数的对象是**64 位字**，并非每个原键。`m_bits[j]` 保存局部
成员位图，`m_sum` 是各字 `popcount(m_bits[j])` 的 Fenwick 树。
例如用八位字作缩尺演示，集合 `{1,6,18,20}` 的四个字计数为
`[2,0,2,0]`。一基 Fenwick 槽依次为 `[2,2,2,4]`：槽 1 管第一个字，
槽 2 管前两个字，槽 3 管第三个字，槽 4 管全部四字。

#### 二进制选择怎样跳到含答案的字

查询后继 `≥7`，当前字 `{1,6}` 内没有答案。前面截至当前字共有 2 个
元素，所以要找全体第 3 个元素。Fenwick 不逐字扫，直接从大到小尝试
跳过计数区间，维护“已跳过的字数 `p`、元素总数 `s`”，且始终 `s<目标秩`：

```text
p=0, s=0
for step 从不超过 M 的最高二进制幂递减到 1:
    next=p+step
    if next<=M 且 s+tree[next]<目标秩:
        p=next
        s+=tree[next]
答案在第 p+1 个字
```

示例目标为 3：尝试跳 4 字时计数 4，过多，拒绝；跳 2 字时计数 2，
接受；再尝试多跳 1 字会到计数 4，拒绝。答案在第三字，也就是零基字 2，
其最低置位为 2，返回 `2*8+2=18`。这些跳步之所以可以直接用 Fenwick
槽，是高位到低位决定的 `p` 保持了对应的二进制对齐关系。

前驱 `≤17` 在当前字内失败，前两个字总计 2 个元素，便选择第 2 个元素
所在的字，再取该字最高置位，得到 6。后继失败于本字时，要找的总是未来
第一个非空字的**最小**元素；前驱则是此前最后一个非空字的**最大**元素，
因此找到字以后无需在字内继续做一般的第 k 个置位选择。

#### 对应到这份源码，而不是模板中其他函数

`main` 调 `set/reset/at/lower_bound/smaller_bound`，最后一个用 `k+1`
实现包含端点的前驱。`lower_bound` 先截断当前字查 `ctz`；失败才做
Fenwick 前缀和与上面的二进制选择。源码 Fenwick 用零基 `m_sum`，
`cursor=-1`，目标是从 0 开始的秩，所以条件写成 `m_sum[cursor+d]≤k`，
与教学的一基 `<目标秩` 是同一件事。`smaller_bound` 在当前字失败时取
先前元素的最后一个秩，找到字后用 `bit_width(word)-1` 取最高位。

文件中的 `kth` 和逐键扫描的 `upper_bound` **都未由本题主程序调用**。
不能把 `upper_bound` 的线性扫描算到该提交的后继复杂度中，也不能把
`kth` 内逐个清位的循环算成每次跨字查询必做的工作。

初始化先读全部 `N` 位并形成各字计数，再把每槽的计数加到 Fenwick 父槽，
建表 `O(N+M)`；`m_icap=bit_ceil(M)` 把字数向上补为二的幂。
成员查询与同字命中是 `O(1)`，实际修改和跨字前后继是 `O(log M)`，
空间是位图和 `O(M)` 个计数。与占用位图相比，即使一字从 5 个元素变为
6 个、仍然非空，也必须更新整条计数路径；它多维护了秩信息，若业务只要
前后继，这笔计数工作可能没有回报。

[`234854.cpp`](../../selected/predecessor_problem/234854.cpp) 的 `main`
实例化 `OY::BIT01::Tree`。每 64 个键打包到 `m_bits` 一个字；`m_sum`
是每个字的 1 位数构成的 Fenwick 树。插删只在成员真的变化时改叶字，
并沿 Fenwick 路径加减计数。查找先在当前字用掩码与 `ctz/bit_width`
找答案；若没有，Fenwick 前缀和确定跳过多少个元素，再用二进制提升
定位含目标秩的字。这不是逐层“非空字”汇总，跨字查询复杂度为
`O(log (N/64))`，加上一个字内位扫描；空间约 `O(N/64)` 字。
匿名 #234853 也记录为 70 ms，但候选池排序在 #234854 之后；两者
时间打平时不能声称前者绝对慢。该族展示了支持秩、选择时可能付出的
额外计数维护开销，与上游 `fenwick.cpp` 的逐键计数也不同。

## 算法贡献、I/O 贡献与下一步

令 `H=ceil(log₆₄U)`、`M=ceil(N/64)`，三条路线的实际取舍为：

| 实现路线 | 边界查询 | 修改 | 存储与适用条件 |
|---|---|---|---|
| 上游 64 叉树 | `O(H)`，顶层向下，利用缓存极值 | `O(H)`，维护占用及极值 | 固定宇宙的嵌套数组；当前代码逐个 1 初始化 |
| 按层位图 | `O(H)`，同叶字命中为 `O(1)` | 最坏 `O(H)`，可在状态未变时停止传播 | 约 `N/8` 字节加小量占用层；批量构建，适合有界宇宙 |
| 位图 + 小集合缓存 | 缓存有效且 `K≤16` 时固定短比较；脏缓存重建 `O(KH)` | 位图更新并标脏 | 额外 18 个缓存槽及基数；连续查询才能充分摊薄重建 |
| #76516 的 vEB | `O(log log U)`；成员查询也借助后继 | `O(log log U)` | 按整个 `U=2^24` 预分配簇，并保留初始位图 |
| #234854 的位图 + Fenwick | 同字 `O(1)`，跨字 `O(log M)` | 实际成员变化时 `O(log M)` | 每字位图加每字计数，适合还需要秩/选择的接口 |

本题只有增删和查找，树结构在查询间不断变化，因此这些代表都按输入顺序
在线执行操作；不能套用静态 RMQ 的预计算去回答更新后的集合。
构建时间也须分开统计：位图与 Fenwick 都能在读完 `N` 个初始位后线性
生成各自摘要；vEB 的 `init` 还要构造预分配簇。单次查询复杂度不包含
读入初始串，也不能用它替代整程序复杂度。

对本题，值得保留和单独测量的是：① 初始串直接打包为位图并逐层归约，
避免对最多一千万个初始位逐一插入；② 按连续 64 位字存储四层，改善空间
局部性；③ 对同字命中、删除后仍非空这些常见情况尽早返回；④ 在同一算法
实现上分别测 I/O、AVX2 初始化和查询分支，才能定位速度来源。
本仓库已有同族实现和 Fenwick 对照，见
[`tutorial.md`](../../../problems/data_structure/predecessor_problem/tutorial.md)。

与上游的**操作级**区别是：初始串直接生成叶字而不是每个 `1` 调一次
递归插入；部分实现仅在空/非空变化时更新父层，展开版插入无条件置父位，
而各版都不必维护每结点的极值；查找用
连续数组、位掩码与 `ctz/clz`，省去递归对象访问。#278227/#269275
的查询代码直接展开固定四层，#403023 则保留可复用容器并加稀疏态缓存。
这些改变均可能影响速度，需要单独做同机消融实验。

输入输出还包括 `mmap`、SWAR 整数解析、AVX2 打包初始串、缓冲和数字查表
输出。它们会改变整程序 OJ 时间，但不会改变集合操作的复杂度。
目前没有相同编译器、相同机器、相同 I/O 下逐项消融的数据，不能把
16/20/48/70 ms 的差别解释为纯数据结构差别。随后应持续更新较大候选池，
在每次测试版本变化后限速重测，再人工查主路径并维护**每个算法族的最快
当前版本提交**；本页只对这 100 条的已审阅范围负责。
