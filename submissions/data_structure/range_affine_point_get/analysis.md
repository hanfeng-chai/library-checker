# 区间仿射修改、单点查询：只保存标记，再把历史快照批量求值

## 1. 题目与时间顺序

数组A支持区间修改A[i]←bA[i]+c（l≤i<r）及单点取值，
结果模998244353。[题面](../../../upstream/data_structure/range_affine_point_get/task.md)
中N,Q≤500000，初值和c允许为0，b非零。

用A=[1,2,3,4]：

| 操作 | 当前数组/答案 |
|---|---|
| 整段应用F(x)=2x+1 | [3,5,7,9] |
| 查询0 | 3 |
| [0,2)应用G(x)=3x+4 | [13,19,7,9] |
| 再查询0 | 13 |
| [1,4)应用H(x)=x+5 | [13,24,12,14] |
| 查询2 | 12 |

逐个修改区间内元素，最坏O(NQ)。
多个连续修改可以合成一个函数：
先F=(a,b)，后G=(c,d)，合成为(ca,cb+d)。
顺序不能交换：G(F(1))=13，F(G(1))=15。
这也是所有lazy标记必须维护时间顺序的原因。

## 2. 上游：通用懒标记线段树，连区间和也一起维护

[correct.cpp](../../../upstream/data_structure/range_affine_point_get/sol/correct.cpp)
的每个数据节点存(sum,len)，标记存一个仿射函数(a,b)。
一个整段应用该函数后：

~~~text
sum <- a·sum + b·len
len 保持不变
tag <- 新函数 ∘ 旧tag
~~~

区间完全覆盖时只更新这个节点，暂不逐个改孩子；
部分覆盖时先把父标记传给两个孩子，再递归并重算父区间和。
点查询实际调用sum(idx,idx+1)，仍走通用区间查询。
时间O(log N)/操作、空间O(N)。

这个基线是正确的，但本题从不询问区间和：
内部sum、len的乘加、返回后的push-up都不是最终所需信息。
公开快解首先省掉这一层数据聚合。

## 3. 对偶线段树：只留下“以后需要执行的函数”

叶子保存初值，内部只保存尚未下推的函数标记。
区间修改分解成O(log N)个完整覆盖节点，把新函数接在它们旧标记之后；
查询一个位置，只需把根叶路径上的函数按正确时间顺序作用于初值。
不维护区间和，就无需从孩子重新合并父数据。

### 为什么修改边界前必须先下推

假设先给整个数组打F，再只给左半打G。
如果直接让根保留F、左孩子保留G，
查询若从叶向根执行，就成了F(G(x))，时间顺序错了。
正确做法是深入左半之前把旧父标记F传到孩子，
再将新G组合到孩子上，形成G∘F。

反过来，若先改左半G，再改整个数组F，
可以让孩子保留旧G、父保留新F；
叶向根执行便是正确的F∘G。
因此维持的不变量是：**尚未下推的祖先标记晚于其下方已有的标记**。
部分区间更新前沿边界下推，正是为了不让较新的子标记越过旧祖先。

标记下推时，孩子已有的函数先执行，父函数后执行，
即child_tag←parent_tag∘child_tag，再把parent_tag清成单位元。
这里不是“沿某个固定树方向永远按输入顺序排列”，
而是更新过程主动维护了可按叶到根求值的不变量。

## 4. 从二叉改成8叉，一次处理整个边界块

分支数B=8时，一层区间分成若干8元素块。
左边界块只改后缀，右边界块只改前缀；
中间完整块则在上一层表示为一个连续区间，继续同样处理。
修改前仍先将两条边界路径上的旧标记从高到低下推。

用B=4缩尺看[1,15)：

~~~text
最左块[0,4)：只改槽1,2,3
中间完整块[4,8)、[8,12)：交给上一层区间[1,3)
最右块[12,16)：只改槽0,1,2
~~~

掩码把要修改的槽设为全1，其余全0；
先同时计算所有槽的新(a,b)，再blend选择保留旧值还是写新值。
8个32位系数恰好进入一条AVX2向量，
同一块内各孩子标记的复合互相独立，适合这种并行。

树高由约19个二叉层降低到7个8叉层。
代价是每次下推/边界更新会处理整个宽块，
而不是只操作一个标量节点；宽度太大也会增加访存与算术。
SIMD改变常数，不能省掉标记的时间顺序和范围不变量。

## 5. 不立即算答案：保存每次查询当时的完整路径

一个单点答案等于从叶初值开始，依次经过每层标记。
各层之间串行依赖，直接算一条链不容易并行。
快解在查询发生时，先把该点的叶值、每层乘数/偏移**按值拷贝**进结果数组，
最后把8条不同查询的同一层放入一条AVX2向量，逐层并行计算。

例如第一节的查询0在第一次F后发生，快照已足以得到3。
后来左半再打G，即使当前数组的A[0]变成13，
先前保存的是旧系数值，不是会变化的树节点指针，
所以最后批量结算仍输出3，再输出第二次查询的13。

更新和取快照保持原时间顺序，只延迟纯计算与输出。
它需要O(RH)结果存储（R为查询数、H为层数），
并不能原样用于每次必须立即返回结果的交互场景。
如果只看“操作循环结束后才打印”，也不能误判为用最终数组回答全部历史查询。

### #269952 / #390917 / #400998：宽标记与查询批处理

WideLazySegmentTree的B=8，按最大N=500000建立7层。
tree_mul/tree_add分数组放系数；底层add存元素值，
高层存尚未下推的仿射标记。
apply先对左右端点路径push，再逐层用左/右/同块掩码更新。
get不求答案，只把7层路径的系数复制到ret_mul/ret_add；
主循环结束后每8条查询并行结算。

内部使用Montgomery32形式和允许[0,2p)的惰性余数。
但最终单参数SIMD reduce为了省运算，省略了约减式中的一部分进位处理，
源码注释仅称其“returns reduce−1”，随后统一在输出加1。
这不等价于对所有可能的零表示做正确归一化。

已用未改源码、GCC的C++23/O2/AVX2编译复现：

~~~text
1 1
0
1 0
~~~

初值0直接查询，正确输出0，#269952实际输出1。
另一个合法例子：初值1，区间[0,1)应用x←x+(p−1)，再查询，
正确仍为0，实际输出998244353。
第一、三份规范化文本相同，第四份执行代码也相同。
本页未为这些额外反例发起OJ hack，也不声称官方AC状态已变化。
这里可研究宽树和批处理思想，但不能直接沿用这个最终约减捷径。

### #393924：同类结构，补齐规范化与结果尾批次

main实例化WideAffinePointTree，按原顺序apply/collect，
最后resolve并输出。
resolve将最后不足8条的补齐槽显式写入零值/单位标记，
再批量乘加，最后调用Simd::normalize，而不是无条件给截取结果加1。
这样额外执行的向量槽都有初始化值，结果也按标准余数格式输出。

它采用toy的按数值范围选择的解析与缓冲输出，
树的代码虽与第一名有共同结构，当前文件不是逐字节相同的源码。
许多附带整数解析接口未在本题主路径调用。

### #399467：在线查询，无需保存O(RH)份路径

TagSegTree只保存val、tag、has_tag；
apply先按边界尾零位和共同祖先范围下推，
再用位运算枚举完整覆盖节点追加新标记。
get是const函数：从叶向根看has_tag，
把遇到的标记直接作用于val[x]，不在查询时下推或改写树。
这与第三节的不变量一致。

文件中另有get_ref、set等会下推的接口，
本题main没有调用；不能把它们的额外写入计入实际查询。
它保留即时返回答案的能力，单次O(log N)、空间O(N)，
但没有宽树和跨查询向量化，实际135ms也混合了I/O与模约减实现差异。

## 7. 与上游对照，以及适用场景

| 方法 | 维护内容 | 查询时机 | 主要取舍 |
