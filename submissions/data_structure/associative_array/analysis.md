# 关联数组：从有序树到连续存储的开放寻址哈希表

## 1. 题目、语义与普通做法

维护键到值的映射，初始所有键的值为0。
操作 `0 k v` 把键k的值设为v，`1 k` 输出其当前值；
没有出现过的键输出0。[参数](../../../upstream/data_structure/associative_array/info.toml)
允许至多10⁶次操作，键和值都在[0,10¹⁸]。
不能用长度10¹⁸的普通数组直接索引，但实际出现的键最多Q个。

| 操作 | 当前非零或已设置的条目 | 输出 |
|---|---|---:|
| 查询7 | 空 | 0 |
| 设置7=12 | 7→12 | |
| 设置9=3 | 7→12,9→3 | |
| 设置7=0 | 7→0,9→3 | |
| 查询7 | 不变 | 0 |
| 查询9 | 不变 | 3 |

值为0完全合法，键0也合法。因此不能随意用“键等于0”或“值等于0”
来判断一个存储槽是否从未使用。

[上游 correct.cpp](../../../upstream/data_structure/associative_array/sol/correct.cpp)
使用std::map<long long,long long>。典型实现为平衡搜索树，
每次查找、设置有O(log Q)最坏界，空间O(Q)，每个节点还含链接和管理信息。
它额外维护键的顺序，而本题不要求有序遍历。

上游查询也写成mp[key]：缺失时插入一个值为0的节点再输出。
这满足题意，却可能为只查询一次的不存在键做分配。
快解专门的get接口在这种情况下直接返回0，不改变表。

## 2. 哈希只决定从哪里找，不能代替比较完整的键

哈希函数h(k)把巨大的键空间映射到有限槽位。
不同键可能映射到同一槽，这叫碰撞，不代表两个键相等。
当前前五采用开放寻址：键和值放在同一组连续槽位中，
碰撞时继续探测后面的槽，末端回到开头。

用容量8、仅用于教学的h(k)=k mod 8举例：

~~~text
set(1,10): h=1，槽1空，写入
set(9,20): h=1，槽1的键是1，往后到槽2，写入
get(9):   从槽1起，比较1不等，再到槽2找到9
get(17):  从槽1、槽2都未找到，到空槽3时返回0
~~~

停止在空槽是正确的：没有删除操作，插入时一定占据探测路径上第一个空槽；
若目标键曾在更后面，那个空槽当时就不可能一直空着。
每个槽还必须保存完整键，才能区别碰撞。
设置已存在键只覆盖值，不能继续插入第二份相同键。

查询的局部不变量是：已经检查过探测序列前面的所有占用槽，
它们都不是目标键；找到目标或遇到第一个空槽才结束。
这个证明不要求哈希完全无碰撞，所以即使分布不好，算法仍可保持正确，
但运行时间可能很差。

## 3. 乘法高位散列在做什么

几份源码先做64位无符号乘法，再取高20位：

~~~text
h = ((key × 常量) mod 2⁶⁴) >> 44
~~~

乘法把键的多个位混合，再截取桶编号；无符号溢出在这里是规定好的模2⁶⁴运算。
乘数为奇数时，乘法在完整64位空间上是一个置换，
但取高20位之后仍有很多键落到同一桶，绝不意味着无碰撞。
它能改变简单连续键、2的幂等输入的分布，固定常量本身也不提供随机化保证。

当前表容量为2²⁰=1048576，大于最多10⁶次操作，
所以即使每次设置一个新键，仍有空槽可终止探测。
最坏装载率接近0.954，长连续簇的成本可能很高。
常说的哈希“平均O(1)”依赖散列分布和装载条件；
对这些公开、固定的乘数，不能声称任意输入都最坏O(1)。
极端碰撞可使单次探测O(Q)、整段O(Q²)，平衡树的O(log Q)保证则不同。

## 4. 连续布局如何改变常数

当前实现通常分三块：

~~~text
key[capacity]     每槽完整64位键
value[capacity]   每槽64位值
used[capacity]    是否占用的位图
~~~

两个64位数组合计约16MiB，位图约128KiB，容量一次性预留。
探测相邻槽时，数组访问具有局部性，也不用为每个新键单独分配树节点。
代价是按容量预留内存，即使实际键很少也保留这些数组；
高装载率下碰撞簇仍会使访问次数增长。

容量是2的幂，递增后用h=(h+1)&(capacity−1)回绕，
等价于对容量取模。另一份写成达到末端就置0，
两者都是在环状槽序列中找下一位置。

此外，键和值最多19位，输出也可能有百万项。
专用整数解析、映射输入和四位数字表会影响端到端时间；
它们与哈希探测的作用应分开测量。

### #362188 / #396628：分开“设置时插入”和“查询时返回默认值”

FastHashMap<uint64_t,uint64_t,20> 的乘数为
11400714819323198485。设置调用operator[]：遇空槽先设置used、
完整键以及V{}，随后赋入新值。查询调用get：遇空槽立即返回V{}，
不设置used、不写键，也不增加将来的探测压力。

两份规范化换行后的文件相同，43/44ms不能归为算法差异。
main用FastIO读op/key/value，文件的count接口未被调用。
表初始化只需清占用位图；在key/value使用前，插入路径保证相应槽已经赋值。

### #278226：显式set/get与另一个固定乘数

HashMap的容量同为2²⁰，乘数为11995408973635179863，
set/get分别实现相同的线性探测不变量。
读取操作码走rd.u1，键和值走rd.ud，输出wt.ud；
算术仍是一次64位乘法取高位加逐槽比较。
没有随机seed，也没有树回退，不能把换乘数描述成对所有恶意键的保证。

### #272998：main用的是OpenAddrHashMap

文件前面还定义了另一份HashMap和全局hash_map，
实际main却创建OpenAddrHashMap hm，并只调用hm.set/get。
后者以vector预留keys、values，用同一个11995408973635179863乘数；
遇空槽时get返回values[h]，因为值数组在构造时零初始化，
且从未使用过的槽不被其他路径写入，返回值正好是0。

此处“不显式return 0”依赖初始化不变量；
把vector改成未初始化存储后不能原样保留get。
输入用十六字节加载与八位组SWAR，再处理尾部；
输出以四位查表拼接并缓冲。

### #400964：不能把文件不完全相同说成算法不同

哈希结构、容量、乘数及main的set/get使用与第一名相同，
但I/O模板增加了整数概念、类型转换和不同的解析入口组织，
所以不能声称整个文件逐字节相同。
实际键和值仍走64位整数读取、查询输出仍走FastIO。
45ms包含解析器和运行环境，不能直接证明其哈希核心更慢。

## 6. 可复用结论和测试重点

前五的共同算法变化是从有序平衡树改成开放寻址表：
减少指针追踪和逐节点分配，并避免查询缺失键时插入。
相应代价是固定容量与依赖散列分布的性能，而非更强的最坏时间保证。

正确性应检查键0、值0、覆盖同一键、不存在查询、碰撞后找键和末端回绕。
性能应固定I/O比较不同容量/装载率和散列，再固定表结构比较读写路径。
官方配置本身包含unordered_map_killer、sparse_keys、2_powers等负载，
说明“随机数据快”并不自动覆盖所有测试分布。

本文核对了五份源码、重复文件和手算探测不变量，没有新的性能benchmark；
43–45ms的单次快照不足以把哈希常量、I/O或布局贡献分别量化。
