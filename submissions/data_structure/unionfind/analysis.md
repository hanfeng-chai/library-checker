# 并查集：从连通分组到路径压缩，以及前五实现的工程取舍

## 1. 题目究竟维护什么

有 N 个点，最初各自独立。操作 `0 u v` 把 u、v 所在的两组连起来，
`1 u v` 询问它们是否属于同一组，输出 0 或 1。
这里的“连通”允许经过中间点；连接 0–1 和 1–2 后，即使没有直接连接 0–2，
它们也在同一组。[参数](../../../upstream/data_structure/unionfind/info.toml)
规定 N,Q≤200000。

| 操作 | 相关分组 | 输出 |
|---|---|---|
| 0 0 1 | {0,1},{2},{3},{4},{5} | |
| 0 2 3 | {0,1},{2,3},{4},{5} | |
| 1 1 3 | 两个不同组 | 0 |
| 0 1 2 | {0,1,2,3},{4},{5} | |
| 1 0 3 | 同组 | 1 |
| 1 4 5 | 不同组 | 0 |

只需要知道分组，不要求恢复连接路径，也没有删除连接。
一个直观方案给每个点存组号，合并时扫描所有 N 个点改组号，
最坏 O(NQ)。另一方案保存图、每次查询 DFS/BFS，
也会重复走大量已经确认的连接。并查集保存组的代表来共享这些信息。

## 2. 用父指针树代表一个集合

每个点保存 parent，沿父指针最终到达根；同一棵树中的点属于同一组。
find(x) 找到根，same(u,v) 比较两根，merge(u,v) 把一个根接到另一个根下。
必须连接根而不是任意两点，否则可能拆坏原来的代表关系或形成环。

例如 3→2→0、1→0，根为 0，表示集合 {0,1,2,3}。
树只是内部表示，不是用户输入的原图；把父指针改得更短，
只要仍通向同一根，就不会改变连通关系。

### 2.1 按大小或秩合并，避免树退化成链

若每次随意把大树接到一个新点下，树可以长成 N−1 条边。
按大小合并时，总把较小集合接到较大集合。
一个点的深度每增加 1，它所在集合的大小至少翻倍，
因此不压缩路径也能保证树高 O(log N)。

上游采用按**秩**合并：秩作为树高的上界，小秩接大秩，
只有两根秩相等时，新根的秩才加一。
压缩后实际树高会下降，但秩无需重新计算，也不应把它继续当成实时树高。

### 2.2 路径压缩，把一次查找的结果留给以后

完整压缩沿父链找到根，再把走过的点直接接到根。
对于 7→6→4→0，查找后可成为 7→0、6→0、4→0。
上游递归式 `parent[x]=find(parent[x])` 正是在递归返回时完成这些改写。

路径折半则每次把当前点接到祖父，再向祖父继续：
上例先改 7→4，再从 4 走到 0；不保证这一次把所有经过的点都直连根，
但省去回程或第二趟遍历，后续查找会继续缩短。
这两种压缩配合大小/秩合并，整段操作具有反 Ackermann 量级的摊还界。
“摊还”针对很多次操作的总成本，不表示每一次 find 都严格只访问固定几个点。

## 3. 上游 correct.cpp 已经使用了两项核心优化

[上游源码](../../../upstream/data_structure/unionfind/sol/correct.cpp)
有 p、r 两条 int 向量：p=-1 表示根，r 初值为 1 保存秩。
group(a) 递归找根并完整压缩；merge 找两根，相同则返回，
否则按 r 连接，相等时增加新根秩。gn 记录组数，但本题不输出它。
main 逐条 scanf 输入，查询时 printf。

这已经是标准的高效并查集，时间为 O((N+Q)α(N))、空间 O(N)。
前五相对它的差异主要在单数组表示、压缩方式和 I/O，
不能把“采用路径压缩”列为上游没有的独有加速。

## 4. 单数组为什么既能存父指针，又能存大小

非根点存非负父编号，根存负的集合大小：

~~~text
p[root] = -size
p[child] = parent_index
~~~

集合 {0,1,2,3} 可以表示为 p=[-4,0,0,2,…]。
负数与合法点编号不相交，因而一条数组就区分了根和孩子。
合并根 x、y 时，若 p[x]>p[y]，x 的绝对值更小，交换两根；
然后 p[x]+=p[y]，p[y]=x。
例如 -2 与 -3 合并后根大小为 -5，符号规则不能写反。

这样省去上游独立的秩数组，同时为按大小合并提供信息。
同一机器字同时承担两种角色，是表示上的节省；根大小和非根父编号
仍各有严格含义，不能对任意 p[x] 都当大小相加。

### #400979 / #393688：把根搜索展开在 same 和 merge 中

same 和 merge 都直接在函数里迭代：
读 p[x]，是负数便结束；否则读 p[p[x]]，
若父节点已经是根就停在父节点，否则令 p[x]=p[p[x]] 并跳两级。
负大小与父指针共享数组，因此必须先检查父是否为根，
不能用负数继续当下标访问。

读操作码用 read_u01，写查询结果用 write_u01，
恰好利用本题输入操作码和答案都只有 0/1。
u、v 则使用小于一百万的整数路径。
源码还按平台选择可提示大页的分配器；
MADV_HUGEPAGE 是操作系统提示，不保证这次运行真的分配了大页，
是否有收益要看实际页使用与地址转换缓存行为。

两份源码统一换行后完全相同。重复用户记录提供两个评测样本，
不增加一种算法。

### #393644：核心并查集相同，I/O 接口不同

同样在 same/merge 中内联根搜索并做路径折半，按负大小合并。
其 main 对操作码也调用 read_u32_lt1e6，
答案调用 write_u32_lt1e6，未使用前两份的单字符0/1接口。
结构热点基本相同，差异主要落在读写与代码组织；
这三份全部5 ms的结果不能量化该特化到底省了多少。

### #367390：预先写满零答案的条件与真实反例

find 是递归的完整压缩，unite 按负大小合并。
main 先把输出缓冲预填成反复的 "0\n"，
每遇到查询只在答案为真时把对应 '0' 改为 '1'，
最后统一输出。这减少逐次写换行和写零的工作。

但 outbuf 只分配 250000 字节，本题最多200000次查询，
每次两字节，实际需要最多400000字节。
main 没有在增长 q 时刷新或检查容量，
而 FastOutput::ensure 即便有定义，也未在此输出路径调用。

这个问题已在本机用未改源码复现：输入 N=1、Q=125001，
接着125001行 `1 0 0`，每个答案都应为1。
GCC编译运行返回0，但末尾输出为 `1\xff`，最后一个 token 不是 "1"。
原因是在索引250000处越界写了'1'，后面的换行未在缓冲内预填；
这与当前 OJ AC 并不矛盾，只表明现有官方测试记录不能证明该容量足够。
本页尚未为这个额外反例发起 OJ hack。

### #222501：通用类实际调用的只是合并与查询

main 使用 UnionFind 的 merge_same 合并和 same 查询。
root 递归压缩，merge_same 根据负大小连接并维护分组数。
源码其他并查集、带权版本、分组枚举接口都没有进入主路径。

输出 w[400000] 与2Q最大需求一致，每次写一个数字和一个换行，
最后一次 write；输入是 MmapReader，参数用固定上界的数字解析接口。
调试状态下的范围检查受 NDEBUG 控制，不能假设所有编译配置成本一样。

## 6. 该怎样复用并验证

核心库适合复用“单数组负大小 + 完整压缩/路径折半 + 按大小合并”。
0/1文本特化和固定输出容量属于题目适配层，容量必须从 Q 的最坏分布推导，
不能按随机测试里查询通常只占一半来预留。

[本仓库教程](../../../problems/data_structure/unionfind/tutorial.md)包含按秩完整压缩、
按大小路径折半等实现及既有测试记录。新的控制变量实验应统一 I/O，
比较压缩策略及单/双数组，再分别测0/1特化和大页提示；
用长链诱导序列、重复合并、u=v、全是查询等输入检查边界。
本页核对了源码和一个容量反例，没有新增性能benchmark。
