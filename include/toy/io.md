# io

[io.h](io.h) 面向 x86-64-v3、Linux、GCC/Clang；系统头文件和类型别名来自
[common.h](common.h)，按项目 `cxx_flags.txt` 编译，不依赖 libstdc++。

```cpp
#include <toy/io.h>
using namespace toy;

int main() {
    Reader in;
    Writer out;
    u64 a = in.read<u64, 19>();       // 绝对值最多 19 位，符号不计
    auto [l, r] = in.read_pair<6>(); // 两个无符号 u32，分别最多 6 位
    out.write(a);                    // 默认换行，也可传 ' '
    u64 values[] = {a, l, r};
    out.write(std::span(values));     // 批量数字输出
}
```

输入约定：stdin 是普通文件；十进制整数合法、可放入目标类型，没有前导零或 `+`，
token 间恰好一个空格或换行，末尾也有分隔符。按已知数量读取，不做错误恢复。
Reader 映射整个文件，末尾补零页，保证 SIMD 尾部加载安全；复制 Reader 只复制游标。
`token()` 借用映射中的 ASCII 字符串，不复制；有额外空白行时由题解显式跳过。
Writer 析构时刷新；`put(char)` 写字符，`append(string_view)` 批量复制文本。

## 位数与批量接口

`read<T, Digits>()` 的位数提示只承诺范围，不承诺分布。省略提示则覆盖 T 的全范围。
小整数使用标量或八字节归约，长整数使用十六字节 SIMD；9～13 位中的完整八位
前缀用两条独立乘法归约。宽整数分块后合并；不超过 38 位的提示可减少宽乘法。
例如 Many A+B 输入不超过 10^18，使用 19 位，而不是完整 u64 的 20 位路径。

`read_pair<Digits>()` 支持 1～10 位的两个 u32。7 位以内一次 16 字节加载定位
两个分隔符；9 位版本把末尾八位装入两个 u64 通道，乘加归约后补第九位；
8/10 位用两个通道处理。所有加载都从当前游标或其后开始，不越过文件开头。
有符号数使用单值接口；给出的上界仍须保证结果可放入 u32。

数字输出按四位分组。5～16 位的结果用长度偏置表与 SIMD 去前导零；
128 位结果按 19 位分块。`write(span)` 每批只检查一次容量，适合已缓存的答案；
Many A+B 用 2048 项结果块，Static Range Sum 用 128 项查询块。

整数解析和格式化热路径使用 `[[gnu::always_inline]]`，批量文本拷贝 append 由
编译器决定是否展开。类内定义隐含 inline；类外定义保留显式 inline，解决多编译
单元定义问题。表格使用 inline constexpr，属于变量。

## 输入范围与校验和题

对 253 道原有题目做过一次源码统计，按题去重、负数按绝对值合并。
常见输入上界集中在模数 998244353、数组/下标范围 5e5，以及数值范围 1e9。

| 数值 | 参数中出现的题数 | 重复读取引用该参数的题数 |
| ---: | ---: | ---: |
| 998244353 | 87 | 77 |
| 500000 | 67 | 34 |
| 1000000000 | 66 | 64 |
| 200000 | 41 | 23 |
| 100000 | 37 | 12 |
| 1000000 | 25 | 7 |
| 1000000000000000000 | 18 | 11 |
| 524288 | 14 | 1 |
| 1000000000000 | 4 | 3 |

“重复读取”通过 verifier 的循环、批量读取方法和简单变量引用推断，
不是完整 C++ 语义分析。间接调用、运行时推导的界和字符串编码的 128 位整数可能漏计；
循环次数、数组长度也可能被计入。它用来定位常见范围，不代表实际输入 token 的占比或分布。
操作类型等写在代码中的小常数需要另外考虑。

例如 `static_range_sum` 包含最多 500000 个 `[0, 10^9]` 的值，
以及最多 500000 对端点 `0 <= l < r <= N`：应同时覆盖 `10^9` 和 `5*10^5`。
模 998244353 的系数实际取值通常是 `[0, 998244352]`。
即使生成器随机，端点经过排序、取值经过筛选后也未必仍然均匀。

`many_aplusb` 的 `digit_random` 先均匀选择位数，再选该位数范围内的值，
一对 A、B 共用位数；128 位版本分别选择两者的位数和符号。它们不是高斯分布。

读入 N、L、R 和 N 个整数，输出和模 2^64。L、R 仅承诺范围，不承诺分布。
输出只有一个数字，主要测读取；两道 `many_aplusb` 继续测完整读写。
16 组均匀数据每组最多约 128 MiB，使大多数读取测试超过 50 ms：

| uniform 编号 | 闭区间 |
| --- | --- |
| 00–03 | [0,1]、[0,9]、[0,99]、[0,1000] |
| 04–07 | [0,10^5]、[0,2*10^5]、[0,5*10^5]、[0,10^6] |
| 08–11 | [0,998244352]、[0,10^9]、[0,10^12]、[0,10^18] |
| 12–13 | [-10^9,10^9]、[-10^18,10^18] |
| 14–15 | 完整 u64、完整 i64 |

边界数据另含十进制位数切换、正负极值、零，以及末尾恰好落在 4096 字节页边界的输入。
独立标程使用标量 fread 解析，校验和自然溢出；不使用 toy 库。

## Writer 布局复查（2026-10-01）

比较当前成员缓冲区、仅删去批量局部 cursor、静态缓冲区、静态缓冲区且删 cursor。
13 题、14 个实际调用程序；三道 sample 用全部测例，其余选输入最大的四例，
convolution_mod_large 选两例。候选通过所选正式测例，并检查 GCC/Clang 产物。
Lenovo 静默、不绑核，完整跑两轮后逐例取较小值；这是诊断子集，不替代各题全量报告。

下表是所选测例 sum（ms）及相对当前布局的变化；正数表示更慢：

|---|---:|---:|---:|---:|
| sample/many_aplusb/main | 196.791 | +0.04% | +1.22% | +1.24% |
| sample/many_aplusb_128bit/main | 326.907 | +0.47% | +0.18% | +0.24% |
| sample/integer_checksum/main | 1662.518 | -0.08% | -1.39% | -1.38% |
| data_structure/static_range_sum/naive | 112.058 | -0.70% | -0.64% | -0.44% |
| data_structure/range_affine_range_sum/main | 788.974 | +0.04% | -0.27% | -0.02% |
| convolution/convolution_mod_large/main | 2800.690 | -0.08% | -0.30% | -0.50% |
| polynomial/inv_of_formal_power_series/main | 169.722 | +0.08% | -0.27% | -0.22% |
| tree/vertex_add_path_sum/main | 929.949 | +0.02% | -0.25% | +0.35% |

保留当前实现。多数算法题的变化不足 0.5%，静态布局在 64 位 Many A+B 的 sum
约慢 1.2%；checksum 虽快约 1.4%，但只输出一个数字，不能把差异归因于数字输出。
静态缓冲区还会使同一 N 的 Writer 实例共享存储。综合性能和接口，收益不足以改库。

汇编显示静态 buf 可以把缓冲区边界、flush 地址变成常量，生产调用中也可能让 p
留在寄存器；格式化输出的地址仍随游标变化，并非所有访问都成为固定地址。
当 Writer 通过引用传给另一函数时，GCC/Clang 的静态 buf + 成员 p 版本仍有每项
写回 p 的代码，静态存储本身不能消除字符指针的别名问题。现有局部 cursor
让批量循环只在结束时写回成员，是几行代码的明确保证。

源码、汇编及两轮 perf 原始记录保存在 `build/io-layout-20261001/`；
这里保留结论和主要数值，阅读不依赖该忽略目录。

输入侧也将 checksum 的成对读取上界从 7 位扩大到 9/10 位复查，全部 22 个测例
通过后静默跑两轮。sum 从 1663.942 ms 变为 1674.527/1685.420 ms；
模 998244353 范围的两种候选均约慢 11.3%，10 位候选在 [0,10^9] 约慢 6.8%。
因此不扩大默认选用范围。新接口在复合树题中有用，并不代表每种输入分布都更快。

本轮未修改 io.h 或题解算法；最终全量数据直接来自重新编译后的生产源码。
